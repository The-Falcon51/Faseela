## Account deletion leaves a farmer's field reports, GPS positions and photos readable, publishable and publicly signable
Fingerprint `faseela/account_deletion/delete_my_account/field-reports-and-media-survive-deletion`

**Claimed root cause.** delete_my_account relies solely on ON DELETE CASCADE from auth.users; farmer_updates, tree_events_public and storage.objects are not linked to the principal by FK and the function performs no explicit anonymisation, retraction or object removal, while the read/publish/sign paths bind to the row (update_id / bucket-wide role policy) rather than to a living principal.

**Description.** private.delete_my_account (the DSGVO Art. 17 self-service path, callable by any authenticated principal including farmers) deletes only the auth.users row and relies on ON DELETE CASCADE to remove personal data. The user-facing prompt promises 'This removes your profile and login. Financial records are kept pseudonymised'. For a farmer the cascade removes profiles, role_applications, private.user_roles, farmer_assignments, mill_assignments and farmer_profiles, but public.farmer_updates.farmer_uid is a plain uuid without a foreign key, so every field report (free-text notes up to 1200 chars, exact gps_lat/gps_lng of where the farmer stood, media_paths) survives unchanged; tree_events_public rows (no FK to the farmer) keep the published notes; and nothing in the repository deletes or re-keys storage.objects under field-media/<uid>/<tree>/ and field-media/<uid>/profile/ (the portrait whose consent record was just cascaded away). The same rows are treated by the project itself as the user's personal data: export_my_data (Art. 15/20) returns farmerUpdates keyed by farmer_uid. After deletion: (a) quality_auditor and admin (has_any_role passes admin for every role) still SELECT every farmer_updates row via RLS and every object in the field-media bucket via the bucket-wide SELECT policy; (b) pending_review rows still appear in list_review_queue and review_farmer_update publishes them - it checks only status and assert_not_self_review (which passes for any non-null, different uid), and notify_user silently no-ops because the auth.users row is gone, so the publish commits post-deletion; (c) tree_media_paths joins tree_events_public to farmer_updates by update_id, not by a living farmer, and the anonymous tree-media Edge Function signs the deleted farmer's photos for public visitors. The deletion contract is therefore not met for non-financial operator-generated personal content, with concrete later readers (auditor, admin, anon) and a later operation (post-deletion publication). Oil-request contact PII after deletion is the peer candidate oil-request-contacts-survive-deletion and is not claimed here. Verifier note: every trace and evidence location was re-read and matches; no later migration adds an FK, trigger or cleanup for farmer_updates, tree_events_public or storage.objects (the only DELETE statements in the repo are the auth.users delete and the two retention purges in prune_monitoring).

## Account suspension sets auth.users.banned_until only; no SQL authorization helper, RLS policy or Edge Function checks it and no sessions are revoked, so a suspended user keeps full access for the remaining access-token lifetime and can hard-delete the account to erase the ban
Fingerprint `faseela/admin_tools/admin_set_user_status/suspension-not-enforced-on-live-session`

**Claimed root cause.** Suspension is implemented purely as a GoTrue sign-in/refresh gate (auth.users.banned_until) while database-side authorization (private.require_user, private.has_any_role/current_app_role, all RLS policies) authorizes on auth.uid() from the stateless JWT and never consults banned_until, and admin_set_user_status does not revoke the target's sessions/refresh tokens. Stale authorization persists for the access-token lifetime, and delete_my_account lets the suspended principal erase the ban record itself.

**Description.** private.admin_set_user_status('suspended') updates auth.users.banned_until = 'infinity' and updated_at, writes an audit row, and nothing else (supabase/migrations/20261026000100_admin_tools.sql:59-63). It does not delete the target's auth.sessions/auth.refresh_tokens rows. The whole server-side authorization chain derives the principal from auth.uid() alone: private.require_user fails only when auth.uid() is null (20261020000200_rpc_core.sql:30-35); private.current_app_role/has_any_role (and therefore require_role and every RLS policy built on them) read only private.user_roles (20261020000100_core_schema.sql:24-48). A repository-wide search shows banned_until is read in exactly three places, none of them an authorization control: the admin user directory ('disabled' flag, 20261020000300_rpc_operations.sql:262), e-mail recipient eligibility (20261026000200_notifications_monitoring.sql:47,60) and onboarding-mail eligibility (20261026000400_profile_onboarding_status.sql:107). The three Edge Functions do not reference it either. The client keeps the session alive (persistSession: true, autoRefreshToken: true, src/supabase-client.src.mjs:22-27). Consequently a user whose browser or Capacitor app holds a not-yet-expired access JWT at the moment of suspension can keep calling every public.* RPC wrapper its role permits and reading every RLS-permitted row until that JWT expires; the ban only bites at the next sign-in or refresh. During that window public.delete_my_account (20261020000500_account_deletion.sql:33-34 -> private.delete_my_account :4-29) succeeds whenever the user has no open investment requests and no active shares; it executes 'delete from auth.users where id = v_uid' (:28), which removes the row carrying banned_until and frees the e-mail address for re-registration, so the suspension leaves no enforceable trace. Operator documentation presents the action as 'Konto sperren' (docs/ARCHITECTURE_AND_OPERATIONS.md:43); the migration comment itself only promises that it 'blocks sign-in and token refresh' (admin_tools.sql:46).

### Trace
1. **entrypoint** `supabase/migrations/20261020000500_account_deletion.sql:33` — public.delete_my_account (representative of every public.* RPC wrapper granted to authenticated): Reachable over PostgREST by any holder of a still-valid access JWT, including a principal whose auth.users.banned_until was set after the JWT was issued.

4. **propagation** `supabase/migrations/20261026000100_admin_tools.sql:59` — private.admin_set_user_status: The only suspension control: sets banned_until = 'infinity'; no deletion of auth.sessions/auth.refresh_tokens, no application-side flag that require_user could consult.
5. **sink** `supabase/migrations/20261020000500_account_deletion.sql:28` — private.delete_my_account: Any RPC succeeds for the suspended uid during the JWT window; this one hard-deletes the auth.users row, erasing the ban and freeing the e-mail for re-registration.

## Realtime DELETE events on role_applications are delivered to every authenticated subscriber regardless of the owner/admin RLS policy
Fingerprint `faseela/core_schema/supabase_realtime-publication/delete-events-bypass-rls-role_applications-pk`

**Claimed root cause.** The publication publishes DELETE for RLS-protected tables (Supabase's default `publish = 'insert, update, delete, truncate'` on supabase_realtime), while the data-isolation guarantee stated at core_schema.sql:337 relies on a SELECT policy that the Realtime DELETE path cannot evaluate because the old record is gone; no REPLICA IDENTITY FULL exists so the leak is bounded to the primary key, and role_applications additionally receives cascaded DELETEs from account deletion.

**Description.** public.role_applications is added to the supabase_realtime publication (core_schema.sql:338-340) with the publication's default publish set (which includes DELETE) and is protected only by an owner-or-admin SELECT policy (core_schema.sql:304-305). Supabase Realtime's documented behaviour is that RLS is not evaluated for DELETE change events: because the deleted row no longer exists, Realtime delivers the old record (primary-key columns only under REPLICA IDENTITY DEFAULT) to every subscriber whose role holds SELECT privilege on the table. `authenticated` holds SELECT on role_applications (core_schema.sql:282-285), so any signed-in investor can open a postgres_changes channel {event:'DELETE', schema:'public', table:'role_applications'} with no filter and receive old.user_id for every removed row. In source the only producer of DELETE WAL records on a published table is private.delete_my_account (`delete from auth.users`, account_deletion.sql:28) cascading through `references auth.users (id) on delete cascade` (core_schema.sql:65); no other published table is cascaded from auth.users or deleted by application code (grep of all migrations). A low-privilege account therefore learns the uuid and exact time of each farmer/mill-operator applicant's account deletion. That uuid remains the pseudonymous key on retained investment_requests/transactions/shares rows (owner-scoped, so not readable by the attacker) and is not exposed by public_tree_profile (which omits farmer_uid); however public.farmer_profiles is directly readable by anon and authenticated (tree_profiles.sql:26-30, policy consent_public or own row), so for farmers who consented to a public portrait an attacker who harvested farmer_uid/display_name/village beforehand can attribute the deletion event to a named farmer (the farmer_profiles row itself cascades away at deletion). Expected impact is low (bare identifier plus deletion event, no financial or contact data); the first-party client never renders Realtime payloads, but the Realtime API is reachable by any authenticated client holding the publishable key.

### Trace
1. **entrypoint** `supabase/migrations/20261020000100_core_schema.sql:338` — alter publication supabase_realtime add table: role_applications (with investment_requests, transactions, shares, farmer_updates, pressing_batches, trees_public) is added to the Realtime publication without restricting publish operations, so DELETE events are emitted to Realtime if the publication keeps its default publish set.
2. **propagation** `supabase/migrations/20261020000100_core_schema.sql:304` — create policy role_applications_select: The only isolation control is a SELECT policy (user_id = auth.uid() or admin). Realtime applies SELECT policies to INSERT/UPDATE new records; for DELETE the row is gone and the policy is not evaluated.
3. **propagation** `supabase/migrations/20261020000500_account_deletion.sql:28` — private.delete_my_account: `delete from auth.users where id = v_uid` is the only source-visible producer of DELETE events on a published table; an applicant with a role_applications row passes the function's preconditions (no open requests, no active shares).
4. **propagation** `supabase/migrations/20261020000100_core_schema.sql:65` — public.role_applications.user_id: `references auth.users (id) on delete cascade` removes the applicant's role_applications row in the same transaction, producing a DELETE WAL record whose old record contains only the primary key user_id (REPLICA IDENTITY DEFAULT).
5. **sink** `src/supabase-client.src.mjs:442` — watchOwnRows postgres_changes subscription: Shows the Realtime API shape available to any authenticated client (`.on('postgres_changes', { event, schema: 'public', table, filter })`); an attacker's own client using table 'role_applications', event 'DELETE' and no filter receives old.user_id of other users' deleted rows. The first-party client itself only re-queries under RLS and does not render payloads.

### Verified evidence
- `supabase/migrations/20261020000100_core_schema.sql:282` — `grant select on ... public.role_applications ... to authenticated` satisfies Realtime's subscribe-time table-privilege check for every authenticated account.
- `supabase/migrations/20261020000100_core_schema.sql:337` — Comment states the intended invariant: 'changes are delivered only to subscribers whose RLS SELECT policy matches' — the DELETE path cannot satisfy this.
- `supabase/migrations/20261101000100_harvest_oil.sql:7` — 'No DELETE anywhere' for oil tables; grep of supabase/migrations finds no `replica identity`, no `delete from` on any published table, and `on delete cascade` from auth.users only on private.user_roles, profiles, role_applications, farmer_assignments, mill_assignments, farmer_profiles — of which only role_applications is published. Exposure is bounded to primary keys and, in source, to the role_applications cascade.
- `supabase/migrations/20261102000100_tree_profiles.sql:27` — public_tree_profile (line 129ff) omits farmer_uid, but public.farmer_profiles is granted SELECT to anon and authenticated (line 27) with policy consent_public or own row (lines 29-30), so farmer_uid of consenting farmers is publicly readable before deletion; the leaked uuid is therefore linkable to a public name only for consenting farmers. Impact remains bounded to the identifier and deletion event.

### Exact blockers

## Transactional e-mail outbox has no per-actor enqueue quota; one verified investor can flood the FIFO queue (drained at <=20 mails/min platform-wide) and delay every other user's transactional mail
Fingerprint `faseela/notifications_monitoring/enqueue_email/no-per-actor-enqueue-quota-fifo-outbox`

**Claimed root cause.** private.enqueue_email (supabase/migrations/20261026000200_notifications_monitoring.sql:28-37) and its callers notify_user (:39-49) / notify_role (:51-61) carry no per-recipient, per-actor, per-template or per-window bound, and the create/cancel RPC pairs (create_investment_request + cancel_investment_request; request_oil + cancel_oil_request) plus the unbounded submit_farmer_update / submit_pressing_batch let an authenticated actor repeat a mail-sending action indefinitely while staying under the open-state quotas. Combined with the strictly FIFO, once-per-minute, 20-row drain (outbox_claim :64-79; outbox_trigger.sql:17-28; send-emails/index.ts:291-307) a single actor's volume degrades mail delivery for all users and converts into operator provider spend. Not decidable from source alone: whether any deployed upstream limit (Supabase API gateway / PostgREST per-key or per-IP request rate limit on /rest/v1/rpc for authenticated users) bounds the cycle rate below the 20/min drain.

**Description.** All business RPCs enqueue e-mail through private.notify_user / private.notify_role -> private.enqueue_email, which inserts into private.email_outbox unconditionally for any syntactically valid recipient. The sender drains the outbox strictly FIFO by created_at: pg_cron invokes the send-emails Edge Function at most once per minute and the function claims p_limit 20 rows and delivers them sequentially, so the whole platform sends at most ~20 mails/min. The business quotas bound concurrent OPEN state only (3 open investment requests / 8 open shares; 3 open oil requests), not rate: private.cancel_investment_request and private.cancel_oil_request free the quota in the same call and send no mail, while every successful create/request enqueues mail. A verified investor (any confirmed e-mail account, no payment required) can loop public.create_investment_request with a fresh 16-char idempotencyKey -> public.cancel_investment_request and enqueue one 'reservation_created' mail per two cheap RPC calls, indefinitely. Variants with staff recipients: an investor holding >=1 available oil allocation can loop request_oil -> cancel_oil_request and additionally enqueue one 'review_needed' mail to every finance_admin and admin per cycle; a farmer can call submit_farmer_update without any rate bound, each call mailing every quality_auditor and admin; a mill operator likewise via submit_pressing_batch. Any producer above ~20 mails/min grows a pending backlog that all later transactional mail for other users (payment_approved, review_needed, reservation_created, oil_request_received, ops_alert) must wait behind, and every queued row becomes a paid provider delivery once sent. Neither private.ops_check nor public_status observes a pending backlog (both look only at status='failed'), so the condition is silent. Verified against source: every trace and evidence line resolves to the cited statement; no later migration replaces enqueue_email, notify_user, notify_role, outbox_claim or the two cancel RPCs, and no rate/cooldown/throttle construct exists anywhere under supabase/migrations or supabase/functions.

### Trace

## Password-reset page accepts any existing session (not only a recovery session) and changes the password without current password or re-authentication nonce
Fingerprint `faseela/reset/updatePassword/password-change-without-reauth-on-any-session`

**Claimed root cause.** The recovery page gates on 'a session exists' instead of 'this session came from a PASSWORD_RECOVERY redirect', and the password update path supplies neither the current password nor a reauthentication nonce, relying entirely on an unverified deployment-side GoTrue policy.

**Description.** public/auth/reset.html loads the shared supabase-client bundle (persistSession: true, localStorage), so any persisted Faseela session is restored on that page. src/supabase-client.src.mjs publishes a 'faseela-auth-state' event for INITIAL_SESSION/SIGNED_IN/USER_UPDATED of that ordinary session (lines 246-247), and public/auth/reset.mjs unhides the new-password form on the first event with a non-null detail (lines 28-35) without any check that the session originated from a PASSWORD_RECOVERY event. The save handler (reset.mjs:48) calls FaseelaBackend.updatePassword, which calls supabase.auth.updateUser({ password }) (supabase-client.src.mjs:329) with no current-password check and no reauthenticate()/nonce. Verified against source: the comment at reset.mjs:2 asserts a short-lived recovery session, but nothing enforces it; the PASSWORD_RECOVERY branch (supabase-client.src.mjs:236-243) only navigates to reset.html and does not hand the page any recovery marker; no supabase/config.toml or other auth configuration exists in the repository. ## Farmer-supplied field media reaches the anonymous tree page without any reviewer seeing it; publish decision binds the report row, not the media objects
Fingerprint `faseela/tree_profiles/tree_media_paths/unreviewed-media-path-trust`

**Claimed root cause.** The publication control for field reports (quality_auditor review in review_farmer_update) covers the farmer_updates row, not the referenced storage objects; tree_media_paths treats u.media_paths as a trusted allowlist; can_upload_field_media and the insert-only storage policy permit creating a referenced-but-missing object after publication; and the auditor client (mapReviewItem) discards media_paths so no reviewer ever views the media before it becomes public.

**Description.** A farmer uploads JPEG/PNG/WebP objects into field-media/<uid>/<treeId>/ (client path, insert-only RLS) and submits a field report whose mediaPaths are validated only for the '<uid>/<treeId>/' prefix, length and absence of '..'
