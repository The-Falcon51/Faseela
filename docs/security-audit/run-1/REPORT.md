## 2. Security posture

The backend consistently routes writes through SECURITY DEFINER logic in schema `private` with `search_path=''`, role checks first, owner-scoped RLS on every public table, deny-by-default grants (including default privileges), four-eyes guards on every review path, idempotent reservations under advisory locks, write-once private storage with path-bound policies, pgp-encrypted oil contact data, a strict `script-src 'self'` CSP with a whitelist-grammar event delegation layer, constant-time token comparison on the e-mail sender, and caller-JWT passthrough (no service_role) in the certificate function. The defects found are at the seams: lifecycle (deletion vs. retained derived data), a review UI that does not show what it publishes, a table grant broader than its RPC projection, and definer functions that do not repeat an RLS predicate. The open leads concern deployed Auth/Realtime/rate-limit settings that the repository cannot show.

### [medium] Account deletion leaves encrypted oil-delivery contact PII attached to the orphaned uid and in the finance review queue
`faseela/20261020000500_account_deletion/delete_my_account/oil-request-contacts-survive-deletion` · confidence {'score': 'high', 'reason': "All decisive facts are static: absent precondition check, absent FK/cascade and absent delete statement are verified in the migrations; Postgres FK semantics guarantee the rows survive; the sink query filters by status only. The only non-source element is the operator settlement step, which the schema's status enum and the function's own error text explicitly provide for."} · likelihood medium / impact medium

**Root cause.** delete_my_account (migration 20261020000500) predates the oil feature (20261101000100) and was never extended: it checks only open investment_requests and active shares, oil_requests.user_id carries no FK to auth.users, private.oil_request_contacts references only oil_requests, and no statement deletes or anonymises oil_request_contacts, so the auth.users delete leaves contact PII behind.

**Intended behavior.** Per the contract stated in the function comment, account deletion removes all personal data and leaves only financial records pseudonymised by the orphaned uid. Encrypted contact records (name, phone, address) are declared PII and should be deleted (or the deletion refused while oil requests are open), and the finance queue should not keep actionable requests for non-existent accounts.

**Trace.**
1. **entrypoint** `supabase/migrations/20261020000500_account_deletion.sql:4` — private.delete_my_account: Authenticated owner calls public.delete_my_account -> private.delete_my_account with confirmation 'DELETE'.
2. **propagation** `supabase/migrations/20261020000500_account_deletion.sql:16` — private.delete_my_account preconditions: Only open investment_requests (16-19) and active shares (20-22) block deletion; oil_requests/oil_request_contacts are not consulted.
3. **propagation** `supabase/migrations/20261020000500_account_deletion.sql:28` — delete from auth.users: Hard delete; cleanup relies solely on ON DELETE CASCADE foreign keys from auth.users.
4. **propagation** `supabase/migrations/20261101000100_harvest_oil.sql:51` — public.oil_requests: user_id uuid not null without any FK to auth.users: rows survive the delete with the orphaned uid.
5. **propagation** `supabase/migrations/20261101000100_harvest_oil.sql:69` — private.oil_request_contacts: request_id references oil_requests only; the encrypted name/phone/address blob is never deleted by any statement in the schema.
6. **sink** `supabase/migrations/20261101000100_harvest_oil.sql:407` — private.list_review_queue (oil_requests / oil_fulfilment): finance_admin/admin receives private.oil_contact(r.id) decrypted for every pending/approved request, including those of the deleted account; review_oil_request (303-354) can still approve/fulfil them.

**Evidence.**

- `supabase/migrations/20261020000500_account_deletion.sql:20` — Active-shares precondition; its error text directs the user to support to 'settle or transfer' shares, i.e. the operator path that makes deletion reachable for a share holder.
- `supabase/migrations/20261020000100_core_schema.sql:195` — shares.status check constraint allows 'transferred' and 'settled'; no migration or RPC ever sets them (operator SQL only), so the deletion path for former share holders is a designed-in operator action.
- `supabase/migrations/20261101000100_harvest_oil.sql:4` — Comment classifies oil contact data (name, phone, address) as PII stored only encrypted in private.oil_request_contacts.
- `supabase/migrations/20261101000100_harvest_oil.sql:7` — 'No DELETE anywhere' for oil tables: no cleanup path exists for contacts; verified by grep that no other migration references oil_requests or oil_request_contacts.
- `supabase/migrations/20261101000100_harvest_oil.sql:117` — allocate_oil allocates only to shares with status 'active', so oil data always originates from a share that at that time blocked deletion; the share later becoming non-active (operator) is the only way both conditions coincide.

- `supabase/migrations/20261101000100_harvest_oil.sql:367` — private.oil_contact decrypts with the Vault pii_key for any request id passed by list_review_queue.
- `supabase/migrations/20261020000300_rpc_operations.sql:237` — private.submitter returns null for a uid without a profile, so list_review_queue does not fail on the deleted account's request; the item is returned with submitter null and a decrypted contact.

**Conditions.** data_state: The user holds at least one non-donate oil request (any status) and, at deletion time, no 'active' shares and no open investment requests. Because allocations only arise from active shares, this requires the operator to have set the user's shares to 'settled' or 'transferred' via SQL beforehand (the path the error message points share holders to). authentication_level: Account deletion is triggered by the authenticated owner; reading the retained contact requires finance_admin/admin (list_review_queue) or database/SQL-editor access.

**Bounded reproduction (target-native, local).** ["Investor A obtains a share (create/submit/review flow), a batch on that tree is certified so A receives an oil_allocation, and A calls request_oil with kind 'delivery' and a contact; a row is inserted into private.oil_request_contacts (harvest_oil 258-261).", "Operator settles A's shares: update public.shares set status = 'settled' where user_id = A (the only way shares leave 'active'; core_schema 195).", "A calls public.delete_my_account with confirmation 'DELETE'. Input: `["select public.delete_my_account('{\"confirmation\":\"DELETE\"}'::jsonb);", "select public.list_review_queue('{\"queue\":\"oil_requests\"}'::jsonb);"]`
Observed: Established from source without execution: after delete_my_account succeeds for a former share holder, the oil_requests row keyed by the orphaned uid and the pgp-encrypted contact (name, phone, postal address) in private.oil_request_contacts persist indefinitely, and for pending/approved requests the decrypted contact is still returned to finance_admin/admin by list_review_queue, contradicting the function's own stated contract that only pseudonymised financial records remain.

**Impact / priority.** Directly identifying PII (name, phone, postal address) is retained after an Art. 17 erasure request and remains decryptable to finance staff and database operators, linked to the uid that keys the retained financial records (defeating the claimed pseudonymisation). Open requests of a deleted account remain actionable in the finance desk. Compliance/privacy exposure rather than confidentiality breach to unauthorised parties; data stays encrypted at rest. — likelihood: Every share holder receives oil allocations after certification and is expected to file delivery/pickup requests; any such user who later deletes the account (necessarily after operator settlement/transfer of shares, the path the UI error points to) triggers the retention automatically. No attacker action is needed, but the prerequisite operator step limits frequency.

**Smallest fix.** Extend delete_my_account to the oil feature: (1) refuse deletion while the caller has oil_requests in status pending/approved (same pattern as open investment requests), (2) delete the caller's private.oil_request_contacts rows (join via oil_requests.user_id) before deleting auth.users, so fulfilled/rejected/cancelled requests stay as pseudonymised bookkeeping without PII, and (3) optionally add 'on delete cascade' from oil_request_contacts.request_id and keep oil_requests/oil_allocations as retained financial records. Also consider a retention job that purges contacts of fulfilled/rejected requests after a fixed period.
`supabase/migrations/20261020000500_account_deletion.sql`:
```
  if exists (select 1 from public.oil_requests
              where user_id = v_uid and status in ('pending', 'approved')) then
    perform private.fail('failed-precondition', 'Cancel or wait for your open oil requests before deleting the account.');
  end if;

  -- Remove identifying contact data of all past oil requests; the requests themselves stay
  -- pseudonymised (orphaned uid) like the other financial records.
  delete from private.oil_request_contacts c
   using public.oil_requests r
   where r.id = c.request_id and r.user_id = v_uid;

```
